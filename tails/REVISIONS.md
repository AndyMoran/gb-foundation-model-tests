# Tails: revisions

Every change to the plan's execution, with its date, commit and reason. For: a reviewer checking what was done against `PLAN.md` (tag `tails-plan`).

Entries before the first real run record implementation choices the plan does not name. Entries after it are deviations.

| Date | Change | Commit | Plan reference |

| 2026-11-17 | `build_days.py` and `score_tails.py` written, before either has run on real data. Neither script reads outturn or a scored forecast before `days.csv` is committed. | this commit | §9 |
| 2026-11-17 | T4's training temperatures come from `lightgbm_weather.LightGBMW.features`, the code that made the scored forecasts. Which training rows exist depends on which INDO half-hours are present, so `build_days.py` reads INDO's timestamps and replaces every value with 1.0 before any array is built. No demand value reaches the selection. `--synthetic` checks that the temperatures match a build on real-valued demand. A cross-check also records each day's minimum over every half-hour of D−366 to D−2. Dropping rows can only raise the minimum, so every day below that window minimum must be in T4; the script asserts this. | this commit | §5, T4 |
| 2026-11-17 | T4 compares the 48 temperatures LightGBM was given for D, one per clock slot. On the autumn clock-change day the repeated hour's second occurrence is not among them, because LightGBM never sees it. T1 and T1b use every half-hour of D. | this commit | §5, T4 |
| 2026-11-17 | `days.csv` lists each set's days with the reason for each. The counts in §5 (set sizes, counts by winter and by month, pairwise overlaps, ties at the boundary, days left out of T2) are in `days.json`. "Winter" means November to March. `day_inputs.csv` gives every backtest day's selection inputs. | this commit | §5, §9.1 |
| 2026-11-17 | NESO's forecast for T2 comes from `code/inputs.neso_forecast` on the publications file. It is checked, day by day, against the `neso` column of `results/attempt2/forecasts.csv` (sha256 891ff503…), which `score_tails.py` scores. That file's outturn must equal `forecasts.csv`'s on every shared half-hour. | this commit | §4, §5 |
| 2026-11-17 | The plan fixes `days.csv`'s hash check but cannot fix the hash before `days.csv` exists. `build_days.py` records it in `days.json`. `score_tails.py` checks it there, and refuses to run unless `days.csv`, `days.json` and `synthetic.json` are committed and unchanged. | this commit | §9.2 |
| 2026-11-17 | A day is scored if outturn and every forecaster except NESO cover all its half-hours; NESO is scored on its own complete days, with the regression on the same days. Days not scored are listed, per set. A set's narrow complement uses the months of its scored days. | this commit | §6 |
| 2026-11-17 | The day-by-day rule for fewer than 10 days is applied to any set with fewer than 10 scored days. The plan names T4; in practice only T4 can be that small. | this commit | §5 |
| 2026-11-17 | H1 is "supported" only if the four T1 conditions hold and, where assessed, the T4 clause holds. If the T1 conditions hold and the T4 clause does not, H1 is "unclear". The plan lists the T4 clause as part of H1 but does not classify this combination. The third headline sentence states the outcome in fixed wording, one per case. | this commit | §7, §8 |
| 2026-11-17 | Synthetic check (`score_tails.py --synthetic`). Errors are built so every metric is known exactly from the design: each half-hour's error is ±A·g, A = 400 MW; a day's share of positive half-hours sets its bias; a 6,000 MW outturn spike fixes the peak. Seven cases cover every headline template and every H1 outcome. The T4-failure case runs only if T4 has at least 10 days. Point estimates must match the design to 1e-9, the design must lie in each 90% interval, and each case must pick its template and H1 outcome. Planted bugs were caught in development: error sign reversed, narrow complement ignoring months, interval rule loosened, and peak error taken as the day's largest error. | this commit | §9.3 |
